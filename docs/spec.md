# kenning: sessions that know about each other

Status: ACCEPTED (2026-11-17). Decisions below; first milestone done, spawn, stop and ownership added on 2026-11-18 (D23 to D34).

## The problem

Work is done by agent sessions (pi conversations) that each run in a folder: a session started from a pasted prompt, a subagent, a dorfl agent. They cannot see or address each other. When work spans several sessions, the human becomes the mail carrier: one session drafts a message, the human pastes it into another, carries the answer back, and checks by hand whether the message is still true.

The reference case is the 2026-11-17 template-tree plan (jolly-roger `docs/plans/template-tree-features.md`, "Parallel lanes"): four lanes (tree, push, triggers, messaging), each its own session in its own repo. The push lane became an orchestrator nobody appointed. It wrote "From the push lane (S1): ..." messages for the human to paste. Its first messages were wrong because it had not read the other lanes; it then found them with memonaut (`recall_sql` by project and date, `recall_thread`) and rewrote them. It is one flow among many, not the only shape to support, but it shows every need below.

## The goal

Sessions talk to each other directly. The human hears only what actually needs them, once, in context, wherever they are. An orchestrator is any session that manages others; it answers what it can and escalates the rest.

## Concepts

- **Session**: one conversation, addressed by its transcript path (the key wherever and memonaut already use).
- **Role**: an optional stable name a session declares, such as `push-lane` or `orchestrator:template-tree`. A role points to whichever session currently does that job, so a fresh session started from the same prompt takes over the address.
- **Presence**: what a live session says about itself: folder, branch, role, state (`running`, `waiting-for-human`, `waiting-for-session`, `idle`), what it is waiting on, a one-line status, its latest output refs (commits, versions).
- **Message**: from a session to a session or role. It carries a `requestId` (exactly-once delivery across retries), a delivery state (`pending`, `delivered`, `superseded`, `withdrawn`), and its provenance.
- **Question**: a message that expects an answer. It stays open until it is answered or withdrawn, and the asker can wait on it.
- **Attention item**: a question addressed to the human. It goes into one attention inbox, not into whichever conversation the human is in.
- **Owner**: the session that spawned another. Ownership is set at spawn and never changes.

## Provenance (the rule everything else depends on)

Every message and answer records its origin: `human`, `agent`, or `human-relayed` (a human's words carried by an agent, with a reference to the original attention item or turn). A session's safety gates (ask before pushing, deleting, publishing, approving) are satisfied only by `human` or `human-relayed` input that traces back to a real human act. An agent can carry a human's "I approve" to another session; it cannot produce one, and the receiver can tell the difference. Hosts show the origin on every delivered message.

## Operations

Exposed as pi tools by the extension, and as a CLI (`kenning ...`) for scripts, dorfl and humans.

- `session_register({role?, status?, refs?, state?, takeover?})`: declare this session's role and presence (D8, D9).
- `session_list`: presence of live sessions, filterable by folder, role, state. Past sessions stay memonaut's job.
- `session_read(target)`: the target's presence, its open questions, and the tail of its transcript (or a summary).
- `session_tell(target, text)`: send a message. The tool returns the target's current presence and open questions alongside the result, so the sender sees what it is talking to (read before send).
- `session_ask(target, question)` and `session_wait(target | questionId)`: ask, then block until answered or until the target finishes its turn, with a timeout.
- `session_answer(questionId, text, { relayOf? })`: answer a question; the only way to close one (D12).
- `session_supersede(messageId, text)` and `session_withdraw(messageId)`: replace or cancel a message that is not delivered yet.
- `human_ask(question, options?, blocking?)`: raise an attention item. An orchestrator raises items on a child's behalf, and may merge several children's questions into one item, keeping the link to each.
- `human_answers()`: the answers to this session's items (also delivered as messages).
- `session_spawn(folder, prompt, { role?, fork?, worktree? })`: start a session owned by the caller. `fork` starts from an existing session's transcript at a point; `worktree` creates one under `~/dev/worktrees/<repo>/<branch>` first.
- `session_stop(target)`: stop the current turn of a session the caller owns.

Delivery depends on the recipient's state: to a `waiting-for-human` session, a message is attached to the next human turn (what happens today by hand); to an `idle` session, it starts a turn; to a `running` session, it is queued for the end of the turn, or steers it if marked urgent.

## Ownership

Archiving or deleting an owner cascades to its owned sessions (with an undo window); stopping affects only the session named. An orchestrator's view of its children comes from ownership.

Ownership is a record, not presence (ADR 0007): which session spawned which, in which folder, with which role and how (through a host, a zellij pane or a headless `pi -p`), set when the new session exists and never changed, kept while the session's transcript exists (D23, D25). An owner owns its children's children too. kenning cannot delete transcripts, so the cascade is a marker a host acts on: `archive` marks the session and everything it owns as one batch, which `undoArchive` restores for 7 days (D24).

## The shared ground stays in git

kenning carries short messages, questions and status. Content stays where it already lives: plans and contracts in a git branch, code in commits, packages on npm. Messages point at those (a ref, a version, a section) instead of copying them.

## Architecture

- **Core** (library): identity, presence, mailbox, questions, attention inbox, ownership, in SQLite under `$XDG_STATE_HOME/kenning/`. Single machine. Safe for concurrent writers (several pi processes).
- **pi extension**: the tools above, presence heartbeats from the session's lifecycle, and inbox delivery for a plain pi process (watch the mailbox, inject at the right moment).
- **CLI**: the same operations, plus `kenning inbox` for a terminal-only human.
- **Host interface**: how a host delivers, spawns and stops. The extension provides the default for a terminal pi (spawn as headless `pi -p` or a zellij pane). A host registers itself per process with `registerHost` (D26, ADR 0008).
- **wherever** (first-class host, in its own repo): delivers through its session pool instead of polling, turns spawns into sidebar sessions under their owner, shows presence, and renders the attention inbox (a panel, a badge, a reply box that routes the answer back) using its existing push and Telegram channels for blocking items. wherever's assistant can read the inbox but is not the inbox.

## Compared with bb (getbb.app)

bb's thread spawn, fork, tell, queue, log, wait, list, stop, lifecycle ownership, manager threads, interactions and managed worktrees all have an equivalent above. Not taken: remote hosts, terminals, browser, files over the CLI, plugins, the IDE (pi tools, webhands and wherever cover these). Added beyond bb: the provenance rule, the attention inbox with orchestrator escalation, git as the shared ground, and working across independent pi processes rather than inside one app.

## Out of scope for now

- Several machines (shyrka). Later, through wherever, which is already reachable remotely.
- Pi Durable. Its ideas are taken (exactly-once `requestId`, a subagent as a real conversation, ownership); a migration is a later question.
- Automatic orchestration policies (when an orchestrator answers versus escalates). The first version gives the primitives; the policy lives in the orchestrator's prompt.

## Decisions

Taken on 2026-11-17 after reading pi 1.4.0's extension API (`docs/extensions.md`, `dist/core/extensions/types.d.ts`, `dist/core/agent-session.js`), memonaut, wherever's `CONTEXT.md` and the 2026-11-17 lane transcripts. Each names the alternative rejected. The ones costly to reverse also have an ADR in `docs/adr/`.

- **D1. The first milestone does not include the wherever host side.** It must load harmlessly in wherever and work agent-to-agent there; the inbox UI and human-turn marking are wherever's own milestone. Rejected: keeping "in wherever" in milestone 1, which needs wherever changes first. The done-when is an automated scenario plus a manual checklist, not a field trial.
- **D2. Provenance is integrity against confused agents, not against a malicious one on the same Unix user** (ADR 0003). kenning never lets an agent produce human-origin input through kenning; forging one means bypassing kenning (writing its database, faking a terminal), which the safety rules forbid. Human acts are: TUI typing (`input` source `interactive`), a kenning slash command (the model cannot invoke one), the CLI only with a TTY and without `PI_SESSION_FILE`, and a host's explicit mark. `human-relayed` requires `relayOf` naming a recorded human turn, and carries the human's verbatim words. A signature field is reserved for a host running as another user. Rejected: claiming the strong guarantee, which is false on one user.
- **D3. Delivery never uses pi's in-memory queues** (ADR 0002). Running: at `agent_before_settle` (entries plus `continue`), or at `turn_end` when urgent. Idle: `sendMessage(..., {triggerTurn: true})`. Waiting for the human: held, shown in a widget and a footer badge, and attached to the human's next run by `before_agent_start`; `/kenning deliver` delivers now. Blocked in `session_wait`: its result. Not live: pending until resume or role takeover. Rejected: `deliverAs` steer, followUp or nextTurn (cannot be withdrawn or superseded, lost on crash) and the `input` transform (mixes agent words into the human's).
- **D4. `waiting-for-human` is declared, not inferred** (ADR 0006): an open blocking `human_ask`, an open `ctx.ui` dialog, or the agent's own `session_register` state. Otherwise a settled session is idle and messages wake it, except while the TUI editor holds text (the human is typing) or `/kenning wake off`. The extension's guidelines tell the agent to raise human decisions with `human_ask`. Rejected: treating every human-started session as waiting (nothing would ever wake) and guessing from the last text.
- **D5. Exactly-once delivery.** `requestId` is unique per sender (default: derived from the tool call id); a message is claimed by one live process with a lease, marked delivered when it is in the receiver's transcript, and reconciled from the transcript at `session_start`. Rejected: marking delivered at hand-off, which loses messages on crash.
- **D6. One poller per process** on `PRAGMA data_version`, every 1 s, `unref`'d, started on `session_start` and stopped on the last `session_shutdown`. Rejected: no watcher (idle sessions could never wake) and `fs.watch` alone (unreliable across platforms and checkpoints).
- **D7. Identity and who registers** (ADR 0004). A session is its absolute transcript path, with its session id stored beside it; `/new`, `/resume` and `/fork` re-register. `--no-session` runs stay out. Subagent children (`PI_SUBAGENT_CHILD=1`) stay dormant in milestone 1; registering them as owned children (`PI_SUBAGENT_PARENT_SESSION`) is the later step. `pi -p` runs register while they run. Inside wherever (its `wherever-dev.server-process` marker) kenning behaves as a headless host. Rejected: registering every process, which floods the list (12 subagents in one second on 2026-11-16).
- **D8. Roles are declared** with the `session_register` tool, the `--kenning-role` flag or `KENNING_ROLE`, as `[a-z0-9._:/-]` strings, by convention `<plan>/<lane>` or `orchestrator:<plan>`. The role is also written to the transcript so a resume re-claims it. Folder and branch are filled in automatically; status and refs are what the agent declares. Rejected: inferring the role from the prompt.
- **D9. Role collisions: the newest claim wins only if the holder is not live**; a live holder keeps it unless the claim says `takeover`, and the old holder is told. A fork inherits the role entry but not the role. Messages addressed to a role resolve at delivery, so a successor gets the backlog. Rejected: refusing always (blocks the restart case) and newest-always-wins (a fork steals a live lane's address).
- **D10. Storage** (ADR 0001): `node:sqlite`, WAL, `synchronous=NORMAL`, `busy_timeout=5000`, every write in `BEGIN IMMEDIATE`, at `$XDG_STATE_HOME/kenning/kenning.db` (`KENNING_STATE_DIR` overrides). Liveness is a pid with the same process start time and boot id, so a crash needs no heartbeat to be detected. The schema has forward migrations: unlike memonaut's index, this database is not a derived cache. Rejected: `better-sqlite3` (native build), a daemon, JSON files.
- **D11. Retention.** Pending messages and open questions are never pruned by age (a message to a role unheld for 7 days shows as undeliverable); finished messages, questions and items are deleted after 30 days; dead presence after 1 day; pruning runs on open, at most daily. Rejected: keeping everything.
- **D12. Questions.** `session_answer(questionId, text)` is added (the spec had no way to close a question). `session_wait` returns on the answer, the target settling without answering, an incoming question to the waiter (to break A-waits-on-B-asks-A deadlocks), timeout (default 15 min, max 2 h) or abort. Rejected: answers as plain tells.
- **D13. The human's inbox in milestone 1** is a footer badge in every live TUI session, `/kenning inbox` (answers typed in a slash command are human), and `kenning inbox` / `kenning answer` on the CLI. A blocking `human_ask` also opens a dialog in its own TUI. `human_ask` takes `onBehalfOf` question ids so an orchestrator can merge children's questions and relay the answer as `human-relayed`. Rejected: injecting items into the current conversation.
- **D14. `session_read`** returns presence (with the session's own status line, the best summary there is), open questions, and the last 6 user and assistant texts (2 KB each, 12 KB total), read backwards from the file end; deeper history is `recall_thread`. Message text is capped at 8 KB to push content into git refs. Rejected: a generated summary on every read (cost, latency, nondeterminism); it may come later as an opt-in paid by the reader.
- **D15. Targets.** A string ending in `.jsonl` is a path; otherwise an exact role, then a unique session-id prefix; ambiguity is an error listing candidates. Rejected: an `@role` sigil.
- **D16. Packages** (ADR 0005): a pnpm monorepo like memonaut, with `kenning` (core and CLI, no runtime dependencies) and `kenning-pi` (extension and skill, `pi install npm:kenning-pi`). Rejected: one package (peer-dependency noise for every non-pi importer) and an `@kenning` scope (not owned).
- **D17. License: AGPL-3.0-only**, like memonaut, wherever and the lanes' repos. Rejected for now: MIT or MPL-2.0, worth revisiting before outside contributions if pi upstream or other harnesses should adopt kenning.
- **D18. Tooling** follows memonaut; the pi dev dependency is `~1.4.0` (the installed pi, and wherever's tested range), not memonaut's stale `^0.80.3`.
- **D19. Spawn outside wherever** (shipped on 2026-11-18, see D28 and D29): a zellij pane when `$ZELLIJ` is set, otherwise a detached headless `pi -p` in its own process group, woken later by `pi --session <path> -p`, with `--session-id` assigned up front. Rejected: an RPC supervisor daemon.
- **D20. The host interface** is exported by the core with the terminal default in the extension: `deliver`, `humanTurn`, optional `notifyHuman`, `spawn`, `stop`, and a change feed. wherever implements it in its own milestone. As built, every member of `KenningHost` is optional; `spawn` and `stop` are specified by D28 and D30, and a host is found through the registry of D26.
- **D21. Tests**: core through its public interface on a temporary state dir; a multi-process writer test; a pure delivery planner; and real `pi --mode rpc` processes on pi-ai's faux provider, each in its own process group, killed by group, with a final check that no test pid survives.
- **D22. Hosts mark human input on the session's event bus.** Before sending a human's text, a host emits `kenning:human-input` `{text, channel}` on `pi.events` (one bus per session, unreachable by the model); kenning's `input` handler records the next matching `extension`-sourced input as a human turn. A mark is valid for 5 s after it is emitted, then dropped (on every new mark and every input) and never matched: a host emits it immediately before the send, and pi runs `input` handlers first thing in `prompt()` and `sendUserMessage()` (measured mark-to-`input` latency on pi 1.4: about 0.1 ms, 0.51 ms worst of 20), so 5 s is 10,000 times the worst case. Without it, a send that never reached the handler (another extension returned `handled`, a terminal pi refused it while compacting) left its mark in the queue of 20, and a later identical `extension` input, such as a scheduled `/standup`, became a human turn that could be relayed as `human-relayed`. Rejected: no expiry (that hole), and an expiry of a few hundred milliseconds (no margin for a loaded event loop, for no gain: a scheduled send of the same text within 5 s of a failed human send is not a realistic case). Rejected for now: asking pi upstream to carry an origin on `prompt()`/`sendUserMessage` and persist it on the user entry, which is the better long-term home; proposed on 2026-11-18 as earendil-works/pi#12291. The 5 s expiry is the backstop: a host that awaits its send also closes the mark (D35).
- **D35. A host that awaits its send closes the mark.** After its marked send attempt settles (the awaited `prompt()` resolved or threw), a host emits `kenning:human-input-end` `{text, id?}` on the same bus, and kenning drops that mark if no input consumed it, so a send that was handled elsewhere or refused while compacting leaves nothing to match, with no window. A mark may carry an `id`; an end with an `id` closes exactly that mark, an end without one closes the oldest mark with that text and no id. An end that comes late (after the run, as an awaited `prompt()` resolves) is a no-op, because the input consumed the mark. A host must not emit it after an extension's `pi.sendUserMessage()`, which in pi 1.4 is fire-and-forget (it returns before the `input` handlers run and reports failures only as `extension_error`), so the end could drop a mark about to match; such a host (the `@wherever-dev/pi` bridge) relies on the 5 s expiry of D22. One known wrong case is safe: a `prompt()` called while pi emits `agent_settled` is deferred and resolves before its input runs, so its mark is dropped and that send is not recorded as human. Rejected: the expiry alone (a window remains), and an end emitted by every host (wrong for fire-and-forget sends). The fix that removes the mark altogether is earendil-works/pi#12291.
- **D23. Ownership is a record that outlives presence** (ADR 0007). A spawn is recorded first (`sp_...`: owner, folder, role, how it was spawned, the first prompt), then bound once to the new session's transcript path when that session exists; the owner never changes, a second owner for the same session and a cycle are refused. Ownership is transitive: `owns(caller, target)` holds for the owner, the owner's owner and so on, because an orchestrator answers for its children's children. `ownedBy(owner)` includes sessions that are not live. A host that spawned a session by its own means records it with `recordOwnership`. Rejected: ownership as a presence field (it would vanish with the process, and a headless child is not live most of the time), direct-only ownership (an orchestrator could not stop a lane its own child spawned), and handing ownership over (the spec says it never changes).
- **D24. Archive and delete cascade as a marker with a 7-day undo window.** kenning cannot delete transcripts, so `archive(session, {kind: 'archived' | 'deleted', by})` marks the session and every session it owns, transitively, as one batch and returns the set; the host hides or deletes them, must not remove a deleted transcript before `undoUntil`, and `undoArchive(batch)` restores the whole batch within the window. `expiredArchives()` lists the marks a host may now make permanent. A session already archived keeps its own batch. Archived headless children are never woken. Rejected: a seconds-long undo toast (a cascade from an orchestrator takes every lane and is often noticed later), 24 hours (shorter than a weekend), and kenning deleting files (a host owns its storage).
- **D25. Retention of ownership: never while the session exists.** A spawn that never came up goes after a day. A bound record goes only when its transcript file is gone, nobody runs it, and it was bound over 30 days ago: pi writes a transcript only after the first assistant message, so a missing file alone proves nothing about a fresh session. An archive mark goes with its transcript, after the longer of the undo window and 30 days. Handled stop requests go after 30 days, like other finished rows (D11). Rejected: pruning with presence after a day, and D11's 30-day rule regardless of whether the session still exists.
- **D26. One host registry per process, on `globalThis[Symbol.for('kenning.host')]`** (ADR 0008). `registerHost(host)` returns an unregister function; `currentHost()` is the most recently registered host, and unregistering restores the previous one, in any order. The registry lives on `globalThis` so that a host holding another copy of the kenning module (the wherever server, the `@wherever-dev/pi` bridge in a terminal pi, a jiti-loaded extension) fills the one kenning-pi reads; the key and the versioned shape `{version: 1, entries: [{host}]}` are a contract. One host serves every session in its process, so a `SpawnRequest` names the owner's session file. Rejected: a module-level variable (a second copy of kenning sees an empty registry), an environment variable (inherited by every child and cannot hold an object; wherever rejected the same for its server marker), and registering through each session's `pi.events` (the server has one host for all its sessions, and the tools need it outside any event).
- **D27. pi's `interactive` source is the human only in the TUI, or at a terminal outside an agent session.** pi reports `pi -p TEXT` as source `interactive` too (print mode calls `prompt()` with the default source), so a headless child kenning spawned, a cron job, or an agent's bash running `pi -p "I approve"` would have counted as the human. Outside `ctx.mode === 'tui'`, an `interactive` input is recorded as a human turn only when stdin is a TTY and `PI_SESSION_FILE` is unset (the CLI's rule, D2), and never inside wherever's server (D36). Rejected: trusting the source alone.
- **D28. How a session is spawned.** `session_spawn(folder, prompt, {role?, fork?, worktree?})` records the spawn, creates the worktree (D32), then uses the registered host's `spawn` if there is one, else the terminal default (D19). The first prompt never enters the child as user input and kenning emits no human-input mark for it: binding the spawn queues it as a message of kind `spawn` from the owner, origin `agent`, delivered by the normal rules and labelled in the child as its owner's first prompt, so the child knows who spawned it (`ownerOf` and the status lines say so too). A host's `spawn` gets `{spawnId, owner, folder, title, role?, fork?, worktree?}` (no prompt to send), starts an empty session, and resolves with `{sessionFile}` as soon as the session exists and is addressable; kenning binds it, claims the role for it, and the idle child is woken by the owner's message. A terminal child gets `KENNING_SPAWN=<spawnId>` and binds itself at its own `session_start`, before `before_agent_start`, so no transcript path has to be guessed (pi names a new file by its creation time); it then re-claims its role from the ownership record on every start. A zellij pane runs an interactive `pi --session-id <id>` with no prompt (an interactive prompt would be the human's words) and is woken by the message; a headless child runs `pi --session-id <id> -p <kickoff>`, where the kickoff is a fixed line saying the session was started by its owner and the text is not the human, and the owner's message joins that run at `before_agent_start`. A real `pi -p` run never wakes itself (a wake at `session_start` made print mode's own prompt fail with "Agent is already processing", measured); a print-mode session inside wherever's server does (D36). `KENNING_SPAWN_COMMAND` (a JSON array, default `["pi"]`) is the command children run. `session_spawn` waits up to 30 s for the bind (measured on the test machine: a headless child binds 0.20 to 0.25 s after it is started) and returns the session file and its presence. Rejected: sending the prompt as the child's first user message (recorded as human in a TUI, and read by the model as the human's), guessing the child's transcript path, and a host that sends the prompt itself (two paths to keep in step, and a host could mark it human).
- **D29. A headless child is woken by its owner.** When a headless child is not running and has messages that arrived after its last stop request and it is not archived, the owner's process starts `pi --session <path> -p <wake kickoff>` for it, under a lease in the ownership record (60 s, or until the child comes up) so two polls or two processes never start it twice. Once up, the next wake waits 5 s after the child's start unless the child exits having read everything; without that gap a child that cannot read its messages was restarted in a tight loop (seen in the first version, in a test). The candidates are one cached query (measured: 3 µs for a session that owns nothing, 42 µs with 5 children). A stop request of any outcome counts as its last stop, so mail older than it waits for a newer message. `/kenning wake off` does not apply: it lives in presence, which a child that exited no longer has. Wake logs are appended to `<state dir>/spawn-logs/<spawn id>.log` and not pruned yet. Only the owner wakes a child: an owner that is not running leaves the messages pending until it resumes or the human runs `pi --session <path>`. Rejected: any session waking any headless session (unrelated sessions starting processes), and a supervisor daemon (D19).
- **D30. Stopping is the current turn only, and never cascades.** `session_stop` asks the registered host's `stop(sessionFile, {by})` first; a host answers `stopped`, `not-running`, or `not-mine` for a session it does not run. Otherwise kenning records a stop request, which the target's own extension acts on at its next poll: it aborts the run that was going when the request was made (`ctx.abort()`), answers `not-running` otherwise, and the session stays alive. A run that ends aborted (a stop, or Esc in the TUI) is neither continued at `turn_end` or `agent_before_settle` nor woken again by messages already pending then; they join the next run, and only a newer message wakes it. Before this, an Esc in the TUI with a message pending was undone at once by `agent_before_settle`. Measured: a host stop reaches the child's idle state in 7 to 60 ms; a stop request ends a headless child's `pi -p` 108 ms after it is made. Rejected: killing the process (ends the session, not the turn), signals (a TUI and print mode handle them differently, and a pid can be reused), and cascading (the spec: stopping affects only the session named).
- **D31. Who may stop.** An agent stops only a session it owns, directly or transitively, through `session_stop`; anything else is refused with the owner's name. The human may stop any session's current turn with `kenning stop <target>`, which is refused like `answer` without a TTY or inside an agent session (`PI_SESSION_FILE`). Rejected: limiting the human to sessions they started (the human is the user of every session on the machine), and letting an agent's bash stop sessions through the CLI (it would bypass ownership).
- **D32. Worktrees live at `~/dev/worktrees/<repo>/<branch>`**, never beside the repo (`KENNING_WORKTREES_DIR` overrides the root; `<repo>` is the repository's top-level folder name), made with `git worktree add <path> <branch>` from `worktree.repo` (default: `folder`). A branch that exists neither locally nor as a remote branch git can track is created from HEAD with `-b`; an existing worktree of that branch is reused; a path holding anything else is refused. Rejected: worktrees beside the repo (they pollute every scan of the repos folder) and refusing a new branch (a lane usually starts one).
- **D33. Subagent children stay dormant**, as D7 says: pi-subagents already owns their lifecycle (it spawns, waits on and ends them), they are numerous and short (12 in one second), and their parent sees their output directly. `session_spawn` is for sessions that live on their own. Registering them as owned children from `PI_SUBAGENT_PARENT_SESSION` remains the later step, now a one-line `recordOwnership`. Rejected: registering them now (the flood D7 measured, for no reader).
- **D34. A fork at an entry is written with pi's own `SessionManager`.** pi's `--fork` copies a whole transcript; for `fork.entryId`, kenning opens the source with `SessionManager.open(source, <the folder's session dir>, folder)` and calls `createBranchedSession(entryId)`, which writes the branch up to that entry as a new session whose `parentSession` is the source and whose cwd is the folder; the child starts on that file with `--session`. A fork without an entry uses `--fork <source> --session-id <id>`. Rejected: copying and truncating the JSONL by hand (pi's entry tree, labels and compaction entries have rules kenning should not reimplement).
- **D36. Inside wherever's server, print and json mode mean a long-lived headless host, not a one-shot run** (amends D28 and D27, added 2026-11-19). wherever runs every server session in pi's `print` mode (`hasUI` false) but keeps it alive and never prompts it on its own, so the rule that a `pi -p` run never wakes itself left an idle wherever session with nothing to deliver its mail, and a session spawned through wherever's host never started, since its first prompt is the owner's message (measured in wherever's bench, `server/test/bench/kenning-delivery.ts`: 0 of 3 delivered, 30 of 30 before the rule). The test is `globalThis[Symbol.for('wherever-dev.server-process')] === true`, set by wherever's SessionPool; the key string is a contract between the packages, read on every check because the marker may be set after kenning-pi loads. `mayWakeItself({mode, inWhereverServer})` in `kenning-pi/src/mode.ts` decides: print or json mode wakes itself only with the marker; every other mode always does. The same question for every other place that branches on mode: an `interactive` input is never the human at a terminal inside wherever (`mayBeTerminalHuman`), because its server sends everything through `prompt()` with the default source and a dev server started in a terminal has a TTY on stdin; a human act there is only a host's mark (ADR 0003). The widget, the inbox badge, the editor check and `human_ask`'s dialog already require the TUI and `hasUI`, which a wherever session lacks, so they stay as they are and `human_ask` polls the inbox like any headless session. Rejected: keying on `hasUI` alone (a real `pi -p` has no UI either, and would bring back the "Agent is already processing" failure), and wherever running its sessions in `rpc` mode or setting a mode of its own (it would have to change for a rule kenning got wrong, and the marker already exists for D7).
